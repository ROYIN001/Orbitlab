### 05.11 กฎวางแผนใหม่ที่ทุก GK (รับจาก PLAN:§11.3)

1. นับ PR ที่ merge จริงต่อเลนเทียบ `pr_estimate` และวัด KPI-33 (lead time), KPI-34 (conflict/rework), KPI-35 (ความหน่วงการตัดสินใจ)
2. ประมาณการใหม่ = PR ที่เหลือ ÷ throughput ที่วัดได้ (throughput = WIP เฉลี่ย ÷ lead time) แล้วคำนวณวันที่ของประตูใน §05.9 ใหม่ ที่ GK1 ให้แทนสมมติฐาน 2.6/1.7 PR/วันและขอบของเลน I ด้วยค่าที่วัดได้
3. ย้ายเฉพาะแพ็กเกจที่ยังไม่เริ่มไปคลื่นถัดไปเมื่อเลนเกินความจุ ไม่ย้ายงานที่ PR เปิดอยู่ และไม่เริ่มหลายคลื่นที่แชร์ไฟล์เพียงเพื่อให้ดูขนาน (PLAN:§11.3); ปรับเพดาน WIP และขนาด PR ตาม KPI-33/34/35 (S18 §18.6)
4. ข้อเท็จจริงที่เปลี่ยนหลังฐาน (เช่น #76–#83 ที่ merge ระหว่างวางแผน) ตรวจบน SHA ปัจจุบันและวางแผนใหม่ที่ GK ถัดไป ไม่แก้กลางคลื่นเงียบ ๆ; R3+ ต่อยอดประมาณใหม่แล้วใน refresh 2026-10-04 (32 PR: 30 ใน K3, 2 ใน K4) และตรวจซ้ำที่ GK1
5. บันทึกการเปลี่ยนใน PROGRESS (แถว "re-plan": วันที่ เหตุผล แพ็กเกจที่ย้าย) แก้ `packages.tsv` และ S05 ผ่าน docs PR (R7.5); เจ้าของอนุมัติก่อนคลื่นถัดไปเริ่ม (D-65)
6. **R3+ ต่อยอดไม่ gate ประตูใด:** ถ้า K3 เกินความจุที่วัดได้ ให้เลื่อนแพ็กเกจ R3+ ที่ยังไม่เริ่มไป K4 ก่อนงานอื่น ยกเว้นส่วนที่เป็นบั๊กของป้ายหรือผลเท็จ (M-PLAN-028 ส่วน source matching, M-BUILD-015, M-BUILD-009), M-PLAN-027 (a11y ถดถอยที่ส่งแล้ว; ทำเป็น PR แรกของเลน B ใน K1–K2 ไม่รอ EQ-13) และ R3.0 ถ้า R4.7 ต้องใช้งบ context
