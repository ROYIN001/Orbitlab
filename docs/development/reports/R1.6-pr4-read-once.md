## What changed

**M-PLATFORM-003 (start-up).** Every start ran the legacy cleanup with `read(legacyId)`: catalogue parse, record parse, then a deep copy (`JSON.stringify` + `JSON.parse` of the whole record), only to compare the originals with it. It now uses `listed()` + a new private `stored()`, which is `read()` without the copy; `read()` is `listed()` + a copy of `stored()`, as before.
- The plan suggested skipping the read when `legacyValues(storage)` is empty. That is not identical output: when the first learner's record is unreadable, the read is what pushes the `legacy-cleanup-pending` notice, and EO-STO-1 compares notices (the shell then shows the recovery line). The parse is kept; the copy is dropped.

**M-PLATFORM-005 (profile list).** One snapshot of the chooser cost 5N+3 storage reads and about 3 parses per learner: `listWithStatus()` → `profileRow()` → `read()` per row, then a second `read()` per row for the counts, then `active()` (a read plus counting) for the open learner's name; and `render()` took a snapshot, `canClose()` a second one and the name screen a third.
- `rows()` (new, public) reads the catalogue once and each listed record once, and returns the rows `listWithStatus()` returned plus each readable row's `values` (not a copy; typed read-only). `listWithStatus()` and `profileRow()` are `rows()`/`row()` with `values` taken out, so their results (key order included) are as before. The raw-bytes lookup that `rawProfile()` had is the private `raw()`, shared with `row()`.
- The menu's snapshot uses `rows()` for the counts. The open learner is named by its readable row when the list has one; otherwise it falls back to `name()` as before, so a read that fails for another row (the list then stays empty) still gives the same `activeId`.
- `render()` takes one snapshot and passes it to `canClose(snapshot)` and `nameForm()`. `canClose()` with no argument (Escape, `close()`) still reads live, as the plan asks.
- Reads per snapshot: 5N+3 → N+1 (18 → 4 with three learners in the durable test, 16 → 4 in the chooser one).

**M-PLATFORM-006 (top-bar name).** `AppProfiles.name()` (and the menu's) used `active()`, which builds a summary and so parses the learner's lessons, designs and experiments to count them. Both now read the record and take `.name`; errors still give `''`.

## Second-agent review

A second agent reviewed `007b039..f581750` for storage: **confirmed 3 of 3 items identical-output**, with no blocking findings. Its own comparison test (not committed) ran 007b039's `repository.ts` and `profile-menu.ts` next to the new ones on the same storage. The setups included visit-only, locked, tombstones, a mismatched or garbage record, `getItem` throwing for one key, and a throwing or invalid catalogue. Status, notices, every read API and error code, both snapshots as JSON, `exportAll()` and every stored byte were compared.

Follow-up, in one commit after the review:
1. **The test's oracle used the new code.** `before()` called `listWithStatus()`, which is now `rows()`, so a key-order bug in `rows()` passed it; only EO-STO-1 caught it. `before()` now inlines 007b039's `profileRow()` and counts and is given the catalogue ids. That sabotage (`{ state: 'ok', ...summary }`) now fails 4 of the 6 tests.
2. **Untested edges of the new `activeId`.** A new test covers two cases. When the open learner's record is damaged after start while other rows read, `activeId` is `null`. When `getItem` throws for another learner, the list is empty and `activeId` is still the open learner. The shell `name()` test now also checks an unreadable open record (`''`). The reviewer's sabotages S2 (`profiles.length > 0`) and S4 (no `name()` fallback) each now fail one test. No test was added for "no open learner" in the shell `name()`. Constructing a second `AppProfiles` in the chooser state loads the real menu after the test ends. The chooser snapshot tests cover `activeId: null`.
3. **In visit-only mode `rows()` handed out the live record's values.** A caller could change the visit's work through it. `row()` now copies the values when the repository is in visit-only mode, and the test changes a returned row and checks that the binding still reads the old value. In durable mode each read parses fresh bytes, so nothing is shared.
- Nit 4 (a storage double that throws a `WorkspaceError` from `getItem` itself): left as is. A real `Storage` throws a `DOMException`, and that is rethrown in both versions.
- Nit 5 (visit-only mode stringifies each row once in `raw()`): left as is. The lazy version cost 68 B of the index chunk, and with R1.6-FU-SEL the two branches would then exceed the 584 B of room. This is visit-only only and changes no output.
