## สิ่งที่ทำแล้ว

- คง 3 default-unit shards และ 2 smoke-browser shards ของ PR; เพิ่ม final evidence gate ก่อนนำผลไปใช้ merge
- Pages เริ่ม unit shards พร้อมกับสาย refresh snapshots/build, แล้วทดสอบ full browser 2 shards บน refreshed artifact ชุดเดียว; aggregate ทุก gate แล้ว rehash artifact ที่ publisher ก่อนปล่อยจริง
- แยก concurrency ของ code release กับ scheduled refresh; refresh same SHA หลบ release ที่กำลังทำ และมี publisher queue เดียวพร้อม main-tip guard ก่อน deploy
- รวม scheduled heavy และ audit เข้า discovery/runner/union เดียว; fleet ใช้ discovery แทนรายชื่อที่ต้องคอยเพิ่มเอง
- ทบทวน heavy inventory จาก 27 files / 246 cases เป็น **33 files / 257 cases** โดยไม่แก้ test bodies หรือ tolerance: เพิ่ม 11 cases ใน six files ที่ขาด และแก้ชื่อเดิมของ MS-10 ให้ตรง test ปัจจุบัน “3.57 s”
- เก็บ collection/gate duration และ structured failure annotations/summary พร้อม raw artifacts; คำอธิบายหลักฐานและ change-to-check map อยู่ที่ [VERIFICATION.md](../VERIFICATION.md)

ไฟล์ heavy ที่เข้าระบบเพิ่ม: `custom-satellite-sixdof`, `historical-docking`, `lesson-packs-sixdof`, `mercury-redstone`, `vostok1-recording`, `vostok1-return`.

## สิ่งที่คนมาทำต่อควรทำ

1. ผู้รวมงานตรวจ diff และตรึง candidate หลังรวม learner/gesture/fuel/UI แล้ว; source เปลี่ยนทำให้รายงานก่อนหน้าใช้รับรองรุ่นใหม่ไม่ได้
2. รัน focused verification และ actionlint ซ้ำเมื่อมีการเปลี่ยน infrastructure เพิ่ม; ตรวจว่า `browserVersion` จาก browser runner ถูกบันทึกจริงทุก journey
3. ตรวจ current-candidate CI รวม final union และ domain acceptance ตาม [change-to-check map](../VERIFICATION.md#change-to-check-map) ก่อน merge
4. หลัง merge ตรวจ Pages refreshed artifact / final union / deployment API success ของ exact merged commit; บันทึก PR, CI run, Pages run, deployed SHA และข้อจำกัดใน progress ledger
5. ตรวจ real enabled heavy/fleet workflow ให้มีผล union ครบตาม scope ก่อนอ้างว่า runtime coverage ผ่าน; discovery ผ่านไม่เท่ากับ flight assertions ผ่าน
6. เก็บ 3–5 comparable real runs ก่อนสรุปประสิทธิภาพ workflow; ครั้งนี้ยังไม่อ้างเปอร์เซ็นต์ลดเวลา เพราะ collection/provenance เพิ่ม overhead ที่ต้องวัดด้วย

## ขอบเขตและข้อจำกัด

ไม่มีการลดจำนวน cases, เพิ่ม tolerance, แก้ test เพื่อผ่าน, blind retry หรือเอา PR artifact มาแทน refreshed release โดยข้าม identity checks. งานนี้ยังไม่เปลี่ยน branch-protection settings ของ GitHub. การรายงานว่าเสร็จด้าน implementation ต้องแยกจากสถานะ merged/published และ scientific acceptance ของแต่ละภารกิจเสมอ.

## R1 final — report-only release follow-up

Pages main push ใช้ Markdown-only exemption แบบเดียวกับ CI: report/progress `.md` ไม่ทำ numerical/browser/redeploy gates ซ้ำ แต่ source/tests/config/data/evidence ที่ไม่ใช่ Markdown ยังทำงานครบ และ commit ที่มีทั้งรายงานกับ source ไม่ถูกยกเว้น. Schedule/manual refresh ยังคง full gates เช่นเดิม.

ตรวจ consumer จริงแล้วมีสาม Markdown inputs ที่ต้อง reinclude ทั้ง CI/Pages และ source provenance: `docs/ROADMAP-PART2-3.md`, `docs/SIXDOF-VEHICLE-DATA.md`, `docs/history/phase4-2026-10-01/T03-CURRICULA-RESEARCH.md`. Path สุดท้ายเป็น test-consumed source evidence ที่ CI เดิมตกหล่น; แก้พร้อม policy parity เพื่อไม่ยกเว้นงานที่มีผลต่อแอป/การตรวจ.

มี regression ตรวจ ordered path parity, report-only vs mixed commits, literal Markdown consumers/provenance และ schedule/manual policy. ผู้รวมงานจะรอ exact application deployment สำเร็จก่อน merge report-only follow-up เพื่อรักษา main-tip guard. Build stamp บนเว็บยังอ้าง deployed application commit จนกว่าจะมี application release หรือ scheduled/manual refresh รอบถัดไป; report commit ไม่ได้แปลว่าแอปบนเว็บถูก build ใหม่.

CI `37096708399` บน candidate `f2d7e4804b7b6664b63b8cceb8bb4d0c1842e802` พบ existing B3 policy violation เพราะ tracked `docs/development/PLAN.docx`; unit shard3 ล้มหลัง job elapsed **6m38s** (test step **6m27s**) ขณะที่ unit/browser อื่นยังทำงาน. นี่เป็น preflight omission: ไม่ได้ตรวจ tracked-file policy ก่อนเปิดงานแพง. ผู้รวมงานเอา Word ออกจาก repository และส่ง identical requested DOCX เป็น Release asset โดยไม่แก้ rule/test ให้ผ่อนลง.

เพิ่ม named `Repository hygiene preflight` ใน CI/Pages plan หลัง Node verification และก่อน create-plan; Pages ยังทำเฉพาะเมื่อ coordination อนุญาต. ทั้งเจ็ด cheap hygiene checks ยังคงอยู่ใน default suite/union เช่นเดิม โดยตั้งใจให้ตรวจซ้ำเร็วเพื่อหยุด policy error ก่อน downstream gates. Timing จาก failed run นี้เป็นเหตุผลของตำแหน่ง preflight ไม่ใช่หลักฐานว่าเร็วขึ้นกี่เปอร์เซ็นต์. Candidate ถัดไปต้องผ่าน current CI ทั้งชุด; failed/superseded run ไม่เป็น acceptance.

## PR71 feedback — metadata ที่อ่านผ่าน API ได้

การอ่าน log/artifact ของ CI `37096708399` จาก environment นี้ถูก Azure blob ตอบ HTTP 403 ขณะที่ GitHub run/job/check metadata API ยังอ่านได้. เพิ่ม `Verification metadata` notice **หนึ่งรายการต่อ final aggregate** ทั้งผ่านและไม่ผ่าน: มี `ok`, exact planned source commit/source-inventory SHA-256, counts expected/unique/missing/unexpected/duplicate/nonpassing ของแต่ละ suite, actual Chromium versions จาก reports ที่ provenance ตรง และ validated build-dist manifest SHA-256. ถ้า plan/identity ไม่ครบแสดง `null` หรือ versions ว่าง ไม่เดาค่าทดแทน.

Notice เป็น allowlisted metadata ต่ำกว่า 2 KiB และ escape annotation data/properties; ไม่ใส่ raw assertions, failure payloads, secrets หรือ download URLs. ใช้อ่านผ่าน check-run annotations API เพื่อดูผลรวมเมื่อ blob download มีปัญหาเท่านั้น ไม่ยกเว้น downloads/checks, ไม่ลด assertions หรือ union gates และไม่เพิ่ม/เปลี่ยน fields ของ stored `union.json`. Regression ตรวจ success/failure, counts/identity ที่คงเดิม, mixed/incomplete provenance, bounded payload และ escaping; file-backed aggregate ยืนยันว่าออกหนึ่ง notice จริงทั้งสองผลลัพธ์. Current-candidate CI/Pages ยังต้องผ่านตามเดิม.

Focused Node checks ล่าสุด **59/59** ผ่าน; actionlint 1.7.7 ผ่านทั้งสี่ workflows และ scoped `git diff --check` ผ่าน. ยังไม่ได้อ่าน notice จาก GitHub run จริงของ candidate ถัดไป จึงต้องให้ผู้รวมงานตรวจ check-run annotations API หลัง final aggregate.
