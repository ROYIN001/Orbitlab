## ปัญหาที่พิสูจน์ก่อนแก้

ใน `src/physics/sim/rendezvous.ts` แรง/torque ของ RCS ถูกส่งให้ integrator ก่อนจำกัดการใช้เชื้อเพลิง ส่วน main engine จำกัด burn duration ด้วย delta-v ที่ต้องการ แต่ไม่จำกัดด้วยระยะเวลาที่ tank จ่ายได้จริง เมื่อ tank หมดยังส่ง `evt.rendezvousBurnDone` และเลื่อนไป burn ถัดไป

เพิ่ม regression ก่อนแก้และรัน `npx vitest run tests/rendezvous-fuel.test.ts`: **6 failed / 1 passed** เมื่อเทียบกับ free-fall baseline ตัวอย่าง zero-fuel main engine มี position error 0.058606 m หลัง 0.5 s; zero-fuel RCS มี position error 0.002916 m หลัง 0.25 s ทั้งที่ไม่ควรมีแรงขับ ความแตกต่างนี้เป็นแรงขับที่เกินจาก gravitational coast ไม่ใช่การห้ามวัตถุเคลื่อนที่ในวงโคจร

## งานที่ทำแล้ว

1. จำกัด powered duration ด้วย `min(step, requested impulse duration, tank lifetime)` สำหรับ main engine; ใช้ rocket equation คำนวณเวลาที่ต้องใช้ และเปลี่ยน mass ตาม flow ใน RK substages
2. ลด burn delta-v ตาม impulse ที่เชื้อเพลิงจ่ายได้จริง และ coast ในเวลาที่เหลือของ step; main-engine scheduling ใช้สูตร duration เดียวกัน
3. ใช้ flow ของ translation และ control torque ร่วมกันเพื่อจำกัด powered duration ของ RCS; ส่งแรง/torqueเฉพาะช่วงที่มีเชื้อเพลิง และ coast แบบ torque-free ต่อจนหมด step
4. เก็บ fuel/mass ให้สอดคล้องกันระหว่าง rendezvous state, spacecraft stage และ frame; tank ไม่ติดลบ
5. ถ้า main burn ไม่ได้ impulse ครบ หรือ approach/TORU ยังต้องใช้ RCS แต่ fuel หมด ให้ยุติ rendezvous ด้วย `evt.rendezvousFuelDepleted` และ `rendezvousFuelDepleted` note; ไม่เพิ่ม burn index และไม่แสดง burn success ยานยัง coast ในวงโคจรได้
6. เมื่อ abort หลังเข้าสู่ rigid approach ให้เก็บ attitude/angular motion ต่อด้วย torque-free rigid integration; ไม่ตรึง attitude ไว้เฉย ๆ
7. ไม่ยกเลิก docking ที่ capture สำเร็จแล้วเพียงเพราะ tank ของ RCS ว่าง กลไก capture ไม่ถูกจัดเป็น manoeuvre ที่ต้องมี RCS fuel
8. ไม่เพิ่ม mutable simulation state, frame schema หรือ recorder schema; command journal และ event clock ใช้ contract เดิม การประกาศ fuel-out เกิดที่ end-of-step ขณะที่การปิดแรงภายใน step เกิดตาม fuel lifetime จริง
9. หลัง named heavy verification พบ degeneracy ของ shared `targetAttitude` ที่จุด Zvezda aft: roll reference เกือบขนานกับ nose ทำให้ projection สูญเสีย orthogonality และ `quatFromMatrix` ปฏิเสธ basis แก้ใน `src/physics/rigid/runtime.ts` โดยสร้างแกน z ใหม่จาก cross product ของ unit x/y เฉพาะเมื่อ `abs(dot(x,z)) > 1e-10` ซึ่งเป็น orthogonality limit เดิมของ matrix validator; basis ที่ผ่านอยู่แล้วใช้ arithmetic เดิม เพิ่ม 3 regression cases ใน `tests/rigid-runtime.test.ts`; ไม่ลด matrix validation tolerance หรือเปลี่ยนข้อมูลยาน

## หลักฐานการตรวจ

ไฟล์ใหม่ `tests/rendezvous-fuel.test.ts` ครอบคลุม 16 focused cases:

- main zero/partial/near-empty fuel, requested impulse ที่เสร็จโดยยังเหลือ fuel และ boundary ที่ impulse สำเร็จพอดี
- exact propellant/flow/mass consistency และ partial powered step ตามด้วย coast
- zero-fuel translation/torque, combined translation/roll fuel sharing, torque-free coast, capture ที่สำเร็จแล้ว และ actual contact/capture ที่เกิดใน step เดียวกับ empty fuel

## สิ่งที่ผู้ทำงานต่อควรทราบ

- integration owner ต้องรัน typecheck/full unit และ release/browser gates บน candidate รวม; named heavy/session/replay checks ข้างต้นผ่านแล้ว และต้องผูกกับ frozen physics hashes นี้ตาม release manifest หากแก้ physics อีกต้องรัน checks ที่ได้รับผลใหม่ก่อน merge
- เมื่อแตะ shared rigid runtime หรือ `targetAttitude` ให้รวม `tests/rigid-flex-golden.test.ts` ใน affected gates ก่อน freeze source เสมอ เพราะ focused runtime/replay/docking tests ตรวจ invariants ได้ แต่ไม่รับรอง arithmetic ของทุก historical flight แบบ bit-for-bit; full CI ครั้งนี้จึงพบ regression ที่ focused 120 cases รอบแรกยังไม่ครอบคลุม
- แก้เฉพาะ fuel/flow invariant ไม่ได้ปรับหลักฐาน thrust/Isp, thruster layout, contact constraints หรือ hardware fidelity ของ Soyuz
- RCS ยังใช้ equivalent-thruster torque-to-flow approximation เดิม (effective arm 3 m) และ fixed estimated inertia เดิม; ไม่ได้เพิ่มค่าฮาร์ดแวร์ใหม่ การทบทวน layout/inertia/CG/actuator sources เป็นงาน R4/R5
- numerical thresholds ข้างต้นเป็นผล agreement ใน fixture ระยะสั้น ไม่ใช่ full-mission docking accuracy หรือค่าความแม่นยำฮาร์ดแวร์ตามแผน §8.5
- event timestamp ยังคง end-of-step ตาม recorder contract เดิม ไม่อ้างว่ามี continuous-time event localization ใหม่ การจัดการ discontinuity/contact แบบละเอียดอยู่ใน R5
- R5 ephemeris/frame conversion, navigation errors, two-body contact/free-drift และ cockpit ยังไม่เสร็จ และต้องไม่ทำซ้ำ R1.4 fuel limiting นี้เมื่อเริ่มระยะต่อไป
