## M-PLAN-031 (P1) — restoring the stored mission wrote over it

**What failed.** `applyStoredMission` (`src/main.ts`) is the restore path at start-up, on entering Explore or Engineer (`restoreWorkspaceMission`) and from Home's "continue" card (`continueMission`, also "Back to my mission"). It called `workspace.adopt()` and `panel.share.apply(stored, 'stored')` → `restoreMission` → `onChange` → `preview()`, and `preview()` stores whatever the panel holds while the origin is `workspace`. `parseMissionDocument` treats a newer document (version > `MISSION_FORMAT_VERSION`, issue `newerVersion`, `mission-file.ts:314`) as usable and reads it as far as this version understands it, and a document with a bad setting is usable with that setting put back to the fallback. So the moment it was restored, `orbitlab.mission` was rewritten in this version's format: fields this version does not know were dropped, and fallback values were saved as if they were the user's. With a design reference the path wrote a second time. This broke the R1 contract (a newer state is refused, not overwritten) and "never save fallback data at render" (§10.1 rule 4).

**Fix** (the persistence guard in `src/ui/workspace-mission.ts`, called from the one restore path in `main.ts`):
- `WorkspaceMission.restoring()` — adopt the panel's mission as the user's and hold it: `persists()` returns false while the stored mission is being read, so the preview inside `share.apply` stores nothing.
- `WorkspaceMission.restored(doc, clean)` — the stored mission is in the panel as `doc`. A clean read (no issue) returns true and `applyStoredMission` stores it once (with its design reference, if it flies). A read with any issue (`newerVersion`, a field reset, or `unusable`) keeps `doc` as held: `persists()` refuses it while the panel's mission is unchanged, and the first change (a panel edit, a quick start, a WebMCP edit) ends the hold and is stored as before. `adopt()` (a link, a file, a lesson) also ends the hold.
- The learner already sees the existing notice: "Mission loaded from the mission saved in this browser, but these settings could not be used …" with "it was saved by a newer version of Orbitlab, so anything this version does not know is left out" (`share.notice.reset`, `share.notice.newer`, en/th/ru). No new string was added.

Contract chosen (read, not persisted until a real edit): the mission is opened in the panel exactly as before, so the learner can fly it; the stored bytes stay as the newer version (or the reset document) left them until the learner changes the mission, at which point the learner's mission is stored in this version's format.

## Notes for review

- **Write count of a clean restore.** The restore preview no longer stores, and a clean read is stored once by `applyStoredMission` (before: the preview's write, then a second write when a design reference flew). The final bytes are the same, except that the single write uses only the design reference read from the document (before, the preview's write could carry the previous in-memory reference if it still flew the restored mission; the next write replaced it anyway). This is the "start-up 2→1" part that S12 §12.3 lists under M-PLAN-028, done here as a side effect; M-PLAN-028 should rebase on it.
- **Unusable documents are held too.** A stored document none of which can be used (`usable: false`) was written over by the fallback mission on restore; it is now kept until the learner changes the mission, so the "nothing … could be used" notice shows again on each start until then. This goes slightly past the two cases named in the plan, under the same rule.
- **The learner's first edit replaces a held newer mission** in this version's format (that is the "real edit" of the contract); nothing in the notice says so in advance. A sentence such as "It is kept as it is until you change it" would need a new key in en/th/ru; not added (owner's call).
- "Fly it" from Build and `designFlown` still store directly; both are the user's own actions.
