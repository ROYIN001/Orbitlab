## What the journey does

One file, two passes in one browser (the runner gives each journey one Chromium): Thai on the `phone-390x844` preset with touch, then Russian on `laptop-1280x800` with a mouse. Each pass opens the app in English and becomes a new learner who picks the language in the page, so the stored language is the learner's choice, not the browser's. A pass that throws is recorded as a failure and the next pass still runs. Once its app has opened, each pass closes its own context and checks its page errors and its requests however it ends, and on a failure takes a screenshot and the page's diagnostics first; a pass whose app does not open is recorded and its context closed.

Every route is taken with the page's own controls: the section list (the tab menus at 1280 px, the sheet on the phone), the brand link to Home and Home's Lessons. Choices are made in the page's own selects and fields, the warp included. WebMCP is used to read only: `get_events` and `read_flight_state`. Values compared bit for bit are read in the page (`window.orbitlab`, as `stage2-preflight` and `fx8-context-loss` read it), not through WebMCP's JSON, which turns -0 into 0, and compared with `Object.is`, which tells -0 from 0.

**The CSV, row by row.** The header is the point-mass columns of `src/ui/csv.ts`. Every telemetry row has all of them, its numbers finite, its time rising, and the last at or after the outcome. ## How it differs from the plan's text

- **Held parts.** Step 7's worksheet DOCX is held back with the teaching tools since #156 (`src/ui/held.ts`, `TEACHER_TOOLS = false`). The journey logs it as held and does not export it. Step 6's results check is held too, but lesson 1.1, the step's other option, is run. When the switch is turned on, the DOCX is still to be added to this journey.
- **LUI-01.** The plan's guard ("Use for the next launch" in the loop inspector) exists in a six-DOF flight. A designed vehicle flies point mass by default; the review offers six-DOF as experimental ("Fly it in six-DOF (experimental)"), which this journey does not take, so LUI-01's own path is not exercised here (`lui01-held-tuning` runs it). What step 3 checks instead is weaker: with the flight paused, showing and hiding the setup changes nothing of the flight.
- **Bit-equal values.** The hand-off envelope and the Orbit section's copies of it are compared bit for bit. The Orbit section's Kepler elements are derived from the state (`handoffOrbit`), so they are not compared. The mass is compared at Build → Launch (the reviewed 7 150 kg) and at Launch → Orbit (the spacecraft's dry mass and propellant left); the student's edit replaces the payload between them.
- **The payload.** Build's "Fly it" carries a payload with no engine, so no propellant would be left to check. The journey changes the payload in Launch to the crewed spacecraft, which has its own engine. That is the student's edit that also takes the flight off the window, so one flight carries steps 4 and 5.
- **Order.** The CSV is exported in step 5, before the lesson replaces the live flight. The offline reload is the imported learner's.
- **Strict validators.** The plan asks each exported file to pass a strict validator. No such validator exists for the backup or the CSV: the backup's reader (`parseWorkspaceArchive`) accepts a missing `createdAt`. The journey checks both itself, as described above. EO-STO-2's storage-record diff (M-PLAN-018) is not merged; the journey compares the stored values directly.
- **CSP.** No policy is set in the app yet (M-PLATFORM-027 step 1), so none is counted.
- **No outbound request.** No such check existed (M-PLATFORM-028 has unit tests only). The journey's own check covers the whole pass, from the context's first request.
- **The rocket.** A headless probe (Vitest, not committed) gave these figures: `remix()` of each catalogue rocket with no changes, `assessReadiness` over five orbits and three masses, and `Simulation` flights. The review rejects a Soyuz-2.1a remix for every orbit and mass tried (no restartable upper stage). A Soyuz-2.1b remix passes it for ISS, Baikonur and 7 150 kg. With the crewed spacecraft off the window, the same remix ends `evt.offTargetOrbit` at T+4135.2 s with only the RAAN missed, the spacecraft burning from T+4063.9 s. `tests/target-plane.test.ts` holds the catalogue Soyuz-2.1a to the same off-window result.
- **Dependencies.** The plan lists M-BUILD-024 (partial, not merged) as a dependency, and S17 asks for M-PLATFORM-061 before cross-system load is added. The owner authorized M-PLAN-025 for GK1 (card `q06` A) while both were open. The journey adds four page loads per pass. None stalled in the runs below. A stall seen on CI should be reported under M-PLATFORM-061, not retried.
- **Left for the GK1 record.** S17 asks `R7.1-<GK>.md` for the candidate's SHA and run id, the journeys that ran, the sabotage results, the viewport × language matrix and the HU-6 link. This report has the journey and its sabotage results on a local build. The candidate's Pages run, the matrix and the HU-6 link belong to the GK1 record PR, which adds them to this file.
