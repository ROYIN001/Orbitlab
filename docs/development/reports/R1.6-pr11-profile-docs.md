## Where the code and the plan or the strings differ (the code was followed)

- **Name length.** The window limits names to 80 characters, and so does the message "up to 80 characters". The repository itself accepts 100 (`repository.ts:40`), and so do imported archives (`archive.ts:49`). The docs give 80, the limit a user meets. A name of 81–100 characters can only arrive through an import file. This is not changed here (docs only).
- **The iPad warning.** S10 lists "คำเตือน iPad" under this item. The in-app warning and the `persist()` button are M-PLATFORM-018 (R1.6 PR10), which is not on main. The guide gives the warning in text, and IMPLEMENTATION-STATUS marks the in-app part as planned.
- **R1.6 PRs not on main.** On the base `23ede7f`, R1.6 PR3 and PR7 were not merged, and the docs described the collision that stopped the pre-profile recordings' transfer as a limitation. Both are merged on main `3e15303` (#132, #139); the docs now describe #139's behaviour (see "After merging main `3e15303`").
- The IMPLEMENTATION-STATUS R3.1 row says that a stored mission of a newer version "is read as far as this version understands it rather than refused". That is still true after #122, which stops writing over it. The new R1.6 row records #122. The R3.1 row is left as it is (one item per PR).

## Review fix: what a read-only tab's export holds

An independent reviewer found one blocking error, and it was right. The export bullet said that
**Export this learner's workspace** "works in a read-only or visit-only tab too (below), so the work
done there can be kept". That is true for a visit-only tab and false for a read-only one:

- a read-only (locked) tab's binding refuses every write (`src/workspace/repository.ts:109`, from
  `setItem` at `:115-118`), so nothing changed in that tab reaches the stored record;
- `prepareChange` returns at once for a locked tab (`:318`), so there is nothing to flush;
- `exportProfile` reads the stored record (`:395-400`, `read` at `:178-183`), which the other tab
  owns and writes.

The `profile-session-safety` journey already pins this: the locked tab's backup equals the bytes
the first tab stored (`tests/browser/journeys/profile-session-safety.mjs:45-47`). A learner who
followed the bullet could edit in the read-only tab, export, close it and lose that work.

The code is right and the guide was wrong, so this is a docs fix with no app change and no new
committed test (no test reads the guide; the app's behaviour is the journey's assertion above).
The failing-before evidence is a second one-off check in the session scratchpad, run on the guide
at `597fd9f` and on the fix:

```
== before (597fd9f)
FAIL export bullet does not say a read-only tab keeps the work done there
FAIL export bullet says a read-only export holds the stored work, not the tab's changes
FAIL read-only paragraph says the export is the stored work
FAIL export bullet still says a visit-only export keeps the visit's work
exit=1
== after
ok   export bullet does not say a read-only tab keeps the work done there
ok   export bullet says a read-only export holds the stored work, not the tab's changes
ok   read-only paragraph says the export is the stored work
ok   export bullet still says a visit-only export keeps the visit's work
exit=0
```

The fix, in `docs/USER-GUIDE.md`:

- The export bullet now says that it works in a visit-only tab, so the work done during the visit
  can be kept. In a read-only tab it saves the learner's work as stored, which is what the other
  tab has saved, not changes made in the read-only tab.
- The read-only paragraph now says that the tab can export the learner's workspace "as stored
  (what the other tab saved, without this tab's changes)".

The README and IMPLEMENTATION-STATUS only say that the read-only tab can export, which is true, so
they are unchanged.
