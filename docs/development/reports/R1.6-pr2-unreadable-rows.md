## M-PLATFORM-004 (P1) — one bad profile record emptied the chooser and broke backups

**What failed.** `WorkspaceRepository.list()` passed every catalogue row through `read()`. One record that is truncated (`parseRecord` → `invalid`) or written by a newer version (`version` 99 → `newer`) made `list()` throw. The menu's `snapshot()` swallowed the error, so the chooser showed no profiles ("No learner profiles yet"); `exportAll()` threw, and the menu's `exportMedia` (which looked its target up through `list()`) threw. The learner could neither reach nor back up healthy profiles. Since PR1 this is reachable with a healthy selected profile (PR1 report, "Known limitation").

**Fix** (S10 acceptance: `listWithStatus()`, raw backup or delete, `exportAll` exports readable rows and reports the skipped ones, `exportMedia` reads only its target, TH/EN/RU text):
- `repository.ts`: new `listWithStatus()` returns one row per catalogue owner: `{ ...summary, state: 'ok' }` or `{ id, state: 'unreadable' | 'newer' | 'missing', name? }` (name is taken from the raw JSON only when it parses and has one; `missing` = a catalogue row with no stored record, added in the review follow-up). New `profileRow(id)` reads only that owner; new `rawProfile(id)` returns the stored bytes exactly. `list()` now returns the readable rows only (same `ProfileSummary` shape) instead of throwing, so `exportAll()` exports the readable profiles. `delete()` accepts an unreadable/newer row (it used `read()`, which threw); it is still the same explicit, owner-locked, tombstoned delete with media removal. Nothing in the read paths writes. `create()`'s 40-profile cap still counts unreadable rows (catalogue keys, unchanged).
- `profile-menu.ts`: the snapshot lists readable profiles as before plus `unreadable` rows; Export all returns `{ skipped }`; new `exportRaw(id)` downloads the stored bytes unchanged (`Orbitlab-<date>-stored-profile-<id>.json`); `exportMedia` uses `profileRow(target)` (falls back to the id as the archive's profile name when no name is readable).
- `profile-dialog.ts`: each unreadable row shows its name (or "Unreadable profile"), the explanation ("This version of the app cannot read this profile …" / "This profile was made by a newer version of the app …"), and two actions: "Save a copy of the stored data" and "Delete profile". Delete opens its own confirmation ("Delete the unreadable profile …?", the permanent-removal warning, copy and audio-export buttons, "Delete this profile's stored data"); disabled when read-only or visit-only. Open/rename are not offered. Export all with skipped rows shows "Backup exported with the readable profiles. Profiles that cannot be read were not included; save a copy of each from the profile list."

**Tests** (`tests/workspace-unreadable-rows.test.ts`; three profiles: healthy legacy, one truncated by 12 characters, one rewritten with `version: 99` plus an unknown field; Locks double; media and download modules mocked):
1. chooser start: `listWithStatus()` = 3 rows `ok` / `unreadable` / `newer` (newer keeps its name), `list()` = the healthy one, bad bytes unchanged;
2. durable start: `exportAll()` exports the healthy profile with its work; `rawProfile()` returns both bad records byte for byte;
3. menu snapshot: healthy row in `profiles`, both bad rows in `unreadable` with state; the whole storage map is unchanged by the snapshot (no render-time writes);
4. menu: Export all resolves `{ skipped: 2 }` and the downloaded archive holds the healthy profile; Save a copy downloads the exact bytes; audio export for the current and for the newer profile resolves;
5. select/rename of a bad row reject and leave bytes; the cap still counts the bad rows (`limit` at 40); explicit `delete()` of the truncated row removes record and media; the newer row and the healthy profile's work remain.

## Not done here / notes for review

- Browser journeys not run (CPU reserved): `learner-profiles.mjs` (S10 asks it to "see the normal rows") and `profile-session-safety` are left to the integration session. The dialog's new rows are not unit-tested in a DOM (the repository has no DOM test environment); the menu host and repository behaviour are.
- **Follow-up R1.6-FU-SEL ("unreadable selected profile keeps the tab visit-only"), not fixed here.** If the *selected* profile itself is unreadable or newer, start-up falls back to visit-only (PR1 behaviour), and the visit-only catalogue holds only that copy, so no bad row (and no other profile) is listed. The selection lives in `sessionStorage`, so reloading the same tab selects the same profile again and the tab stays visit-only on every reload; only a new tab (empty session selection with several profiles → chooser) reaches the chooser and the rows added here. Proposed fix (separate PR, storage review): when the selected record reads `invalid`/`newer`/missing, open the chooser instead of visit-only (clear the session selection, push a notice) so the row with its copy/delete actions is reachable in the same tab.
- Export all with no readable profile (all rows unreadable/newer/missing) downloads nothing and shows "No profile could be read, so no backup file was made. Save a copy of each profile from the profile list." With no profiles at all the behaviour is unchanged.
- `exportRaw` file is the stored record JSON, not a workspace archive; it cannot be imported by this version (by design: it is the bytes this version cannot read).
