## ADR: amendment to R1.1 (D-68)

There is no `docs/development/adr/` on this base, so the amendment is recorded here.

**Amends:** [R1.1 storage report](R1.1-storage.md), "Ownership and media": *"Their original legacy transfer is an idempotent single-database transaction. … Media migration collisions preserve both old and owned recordings and leave migration pending; they are not silently resolved by deleting either recording."*

**Context.** A legacy recording (from before learner profiles, keyed by mission only) moves to the first learner (`legacy-v1`) at the first start. A collision happens when that learner already has its own recording for the same mission. This can happen, for example, when an earlier start could not finish the move and the learner then uploaded audio for that mission. Under R1.1, one collision aborted the whole transaction. All the other legacy recordings stayed invisible. The notice told the learner to reload, which could never succeed. Every later start walked the media store again under the catalogue lock (M-PLATFORM-010, CR:B5, CR:NEW-storage-5).

**Decision (owner, D-68 (ก)).** Recordings move one track at a time, each in its own IndexedDB transaction:
1. A track whose owned key (`legacy-v1:<mission>`) is free moves: the owned copy is put and the original is deleted in the same transaction.
2. A track whose owned key is taken stays where it is, unowned. Neither copy is changed or deleted. The learner keeps their own recording, which is the one that plays.
3. A move that fails (for example a quota error) keeps that original and does not undo the moves before it. The migration stays pending, and the next start retries only what is left.
4. The migration is marked done (the existing `mediaMigrated: true`) once every track was either moved or left in place, so later starts do not walk the store again.
5. On the start that finishes with recordings left in place, the learner is told in three languages that some original audio was not moved and that both copies are kept.

**Kept from R1.1.** No recording is ever deleted or overwritten by the migration (the R1 contract, §10.1 rule 4). Already-owned records are never reassigned. Another learner's audio is untouched. The move stays idempotent. Profile JSON and media are still not claimed to share a transaction.

**Consequences.**
- Learners get every recording that does not collide.
- "Reload to retry" now appears only when a move really failed, and a reload can then finish it.
- The contract change is deliberate. The R1.1 assertion `migrateLegacyMedia(…).rejects.toThrow()` became `.resolves.toBe(1)`, as D-68 allows ("the changed test assertion is an intended contract change, not a golden rewrite", `decisions.tsv` row D-68).
- Known limit: a colliding original stays on the device, unowned, but nothing in the app lists it after the start that reported it (see the code-versus-plan notes).

## Code versus plan

- **Catalogue format: unchanged.** D-68's proposal text (S08) says the catalogue records `mediaMigrated` "with the list of collisions". This PR does not write that list. The colliding originals stay as the only unowned records in the media store, so the list can be read from the store itself, and the catalogue format does not change. Writing a list into the catalogue would be a new field in a stored record, which §10.1 rule 9 makes a reader PR and a published release first. S10 §10.1 rule 9 names this only as a condition: "M-PLATFORM-010 if D-68 changes the catalogue format".
- **"Keep both / choose" action: not in this PR.** The same proposal offers the learner a "keep both / choose" choice. The S10 PR table row for this PR asks only for the IDB double, the assertion per D-68 and three-language text that matches the behaviour, so this PR delivers that. The result today is "keep both", with the learner's own recording in use, and the notice says so. A later "choose" action (a dialog row that lists unowned originals from the store and lets the learner swap or delete one by explicit command, §10.1 rule 2) needs its own UI and strings. It can be built without a catalogue format change.
- **Where the text lives.** The notice is the shell's profile status line (`#profile-storage-notice`), shown before the profile menu loads. Its text therefore goes in `src/ui/profiles/context-text.ts`, the shell part of the profile mini-i18n that `src/ui/profiles/text.ts` spreads into `PROFILE_TEXT`. `src/i18n/*` is not touched.

## What failed

`migrateLegacyMedia` (`media-ownership.ts`) walked the store with one read-write cursor. For each legacy record it checked the owned key, and it called `store.transaction.abort()` on the first collision. One collision therefore rolled back every move. `initialize()` (`repository.ts`) caught the rejection, kept `mediaMigrated: false` and raised `media-migration-pending`, whose text says "Reload to retry the transfer". The next start ran the same walk, hit the same collision and aborted again.

## Fix

- `media-ownership.ts`: `migrateLegacyMedia` lists the legacy keys in one read-only pass. It then opens one connection and moves each track in its own read-write transaction. Each transaction reads the original and the owned key and checks again that the original is still unowned. A taken owned key is counted and left alone. A failed move is remembered, and the loop goes on. After all tracks the function rejects if any move failed, and otherwise resolves with the number left in place.
- `repository.ts`: `WorkspaceMedia.migrate` may resolve with that number (`Promise<number | void>`; existing adapters that resolve with nothing still fit). After a successful migrate the catalogue is marked done as before, and `media-collisions-kept` is added to `notices` when the number is above 0. A rejection still keeps `mediaMigrated: false` and raises `media-migration-pending`.
- `session.ts`: the lazy adapter returns the number.
- `app-profiles.ts`: the status line shows `mediaCollisionsKept` for that notice, after the pending case and before the generic recovery text.
- `context-text.ts`, new key `mediaCollisionsKept`:
  - en: "Some original audio was not moved: this learner already has audio for that mission. Both copies are kept."
  - th: "เสียงเดิมบางไฟล์ไม่ได้ย้าย เพราะผู้เรียนนี้มีเสียงของภารกิจนั้นอยู่แล้ว ยังเก็บไว้ทั้งสองไฟล์"
  - ru: "Часть исходного аудио не перенесена: у учащегося уже есть аудио для этой миссии. Сохранены обе копии."
- `media.ts`: the module comment now says that one transaction owns each delete and each track move.

## Notes for review

- One transaction per track replaces one transaction for all of them. That is the D-68 change. Each move still puts the owned copy and deletes the original atomically, and each transaction checks again that the original is still unowned, so a track is never moved twice and never moved half-way.
- The notice appears only on the start that finishes the migration. The catalogue format is unchanged, so nothing remembers it afterwards. The originals left in place are still in the store for a later "choose" action.
- `mutateTracks`/`deleteProfileMedia` are unchanged.
