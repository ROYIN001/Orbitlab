Three one-line files beside the copy re-export those live modules: `ref/projects/validation.ts`, `ref/projects/archive.ts` and `ref/experiments/notebook.ts`. So no line of the copy had to be edited. The copy is frozen; what it imports is not.

**The harness** (`tests/eo-sto/harness.ts`) runs one list of steps on two fresh "browsers": one with `src/workspace` and one with the reference copy. Each browser has one disk (localStorage), Web Locks and a media store shared by its tabs, and a separate sessionStorage for each tab. The clock is faked: 2026-10-07T08:00:00Z, plus one second for each step. After every step the harness compares the two runs byte for byte:
- every localStorage key and value;
- each tab's sessionStorage;
- the step's return value, or its error name and code;
- each tab's status, notices and binding (profile, epoch, valid or sealed, durable or visit-only);
- the media calls made so far.

The first difference is reported with its step, its place (for example the localStorage key) and the two texts around the first different character. This is what S10 asks of EO-STO-1 in the M-PLATFORM-007 row: "storage map, ค่าที่คืน และรหัส error ต้องเท่ากันทุกไบต์".

`MissionPage` in the harness plays `src/main.ts`'s mission storage over a learner's binding. It covers start-up, preview, `loadViewerMission`, `applyStoredMission` (with the M-PLAN-031 hold and the design reference), `restoreWorkspaceMission`, `openTemplate`, and "Fly it" with `designFlown`. The doc comments give the line numbers on 23ede7f. With it, the same steps cover the §10.3.1 paths.

**The sequences** (`tests/workspace-eo-sto-1.test.ts`, 4 sequences, 54 steps):
1. **Start-up, typing, two tabs, an outside writer, a full disk.**
   - A first start migrates originals from before profiles: good values, an unreadable value, a newer value and a device-only value.
   - Typing saves once per keystroke.
   - A save over unreadable and newer values puts them in quarantine.
   - A preference is removed, and a key outside the workspace is refused.
   - A second tab on the same learner is read-only: it reads, and its writes are refused.
   - Writes cross between the tabs, and another writer replaces the record.
   - A full disk refuses a save, and nothing is half-written.
   - A caller changes the backup object it was given, and the stored work does not change (the M-PLATFORM-007 rule "never hand a cached object to code that changes it").
   - Reloads with an original left and with none left (the M-PLATFORM-003 path).
   - The first tab closes and the second takes over.
2. **Learners.**
   - Create, rename, and a second tab that picks a learner from the chooser.
   - A record cut short and a record with version 99, shown through `listWithStatus`, `list`, `rawProfile` and `profileRow`; selecting the bad one is refused.
   - Reset of one lesson (the old binding is fenced), then reset of exams.
   - Export and Export all, as the exact saved text from `workspaceArchiveText`.
   - Import as a new learner, into a learner (keep and replace), and import all.
   - An import whose mission is unreadable is kept in quarantine; a newer backup and a broken file are refused.
   - The 40-learner limit.
   - Deleting the unreadable learner, then the active one.
3. **Visit-only.**
   - A browser without Web Locks: the work stays in memory, delete is refused, and a backup still works.
   - A tab with locks then migrates.
   - A catalogue from a newer version, then one that cannot be read.
4. **§10.3.1 mission paths.**
   - A mission stored before #77/#80 is restored at start-up in Engineer.
   - Home's first-launch template stores nothing, and entering Engineer keeps both the template and the stored mission.
   - Changing the template stores it.
   - "Fly it" stores `design`, and a reload restores the mission with its design.
   - "Continue in Orbit" builds a hand-off whose `origin.design` survives `parseHandoff`, and nothing is stored.
   - A read-only second tab plays the same paths (start-up, template, Engineer, a change, "Fly it", and Home → template → Explore), and nothing is stored.

Each sequence also checks that it did what its labels say, so a match can never be two runs that both failed at the start. For example: `durable`, `locked`, `["th","throws WorkspaceError: locked"]`, `newer`/`unreadable` rows, `stale`, `limit`, `chooser`, and the mission bytes after each §10.3.1 step.

## Findings for later PRs (not changed here)

1. **A clean restore writes the stored mission again from what this version understands.** `applyStoredMission` (`main.ts:1158-1173`) re-saves a stored mission of this version that it read with no issue. Unknown top-level keys and unknown `DesignRef` fields are then dropped, because `parseDesignRef` returns only the six known fields. A probe (not kept) showed this. The stored `"design":{…,"edited":false,"buildStamp":"b-42"},"note":"from a later build"` came back as `"design":{…,"edited":false}` after one start-up. Nothing writes such fields today, so nothing is lost now. But M-PLAN-028 (R3.1r) plans new `DesignRef` fields (Share/export, build stamp). Under §10.1 rule 9 ("ตัวอ่าน … คงฟิลด์ที่ไม่รู้จักไว้เมื่อบันทึกซ้ำ") it needs a published reader that keeps them first, and today's reader does not. For the same reason, an unreadable `design` is removed from the stored bytes at the next clean restore; the mission itself is kept, as tested. No test here pins either behaviour, so a later fix is not blocked.
2. **Byte identity of a restored design depends on field order.** The restored design's bytes are equal only because `designRefFor` (Build) and `parseDesignRef` (restore) list the fields in the same order. The harness found this: its first fixture listed them in another order, and the bytes changed on reload while the content was the same. Any new `DesignRef` field (M-PLAN-028) has to go in the same place in both functions.
3. **The reference copy and later PRs.** An identical-output PR (S07) runs EO-STO-1 unchanged and leaves `tests/eo-sto/ref/` alone. A PR whose stored bytes move in these sequences is not identical-output (S10 §10.1 rule 3, the S07 stop rule) and must say so. Whether such a PR then copies `ref/workspace` again from main, in a commit of its own, is for its review; this PR does not decide it.
