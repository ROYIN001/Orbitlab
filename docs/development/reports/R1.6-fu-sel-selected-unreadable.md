## The bug

If the learner selected in a tab has a record that reads `invalid` (cut short), `newer` (written by a newer version) or `missing` (a catalogue row with no record), `initialize()` threw inside `read(selected)`. Its catch then opened the visit-only workspace. That visit-only catalogue held only a copy of the selected id, so no other learner and no row with the PR2 copy/delete actions was listed, and nothing was saved. The selection lives in `sessionStorage`, so every reload of that tab did the same. A new tab did too when the bad learner was the device's only learner (a new tab selects the migration owner automatically).

## Fix (`src/workspace/repository.ts`, `initialize()`, +9 lines)

When `read(selected)` throws `invalid`, `newer` or `missing`, and the catalogue still reads (the review follow-up re-reads it first, so a catalogue that became newer or unreadable while the owner lock was awaited still goes visit-only):
1. release the owner lock it just took;
2. push the error code as a notice (the shell then shows the existing "Saved data or the learner selection needs attention…" line, `recoveryNotice`);
3. set the tab's selection to `''` (an explicit empty selection means the chooser, so the reload is the chooser too);
4. set the status to `chooser` and return.

Every other error (storage, a catalogue that is newer or cannot be read, `pending`) still falls back to visit-only as before. Nothing is written to `localStorage`, and the bad record's bytes stay as they are. The chooser lists the row with its state (PR2), with "Save a copy of the stored data" (except `missing`) and "Delete profile".

`tests/workspace-profiles.test.ts` "M-PLATFORM-001: releases the owner lock when the selected record is truncated" (R1.6 PR1) asserted the behaviour this bug is: `status === 'ephemeral'`, followed by a visit-only write. It failed after the fix (`expected 'chooser' to be 'ephemeral'`). The owner approved changing it (card q15, option A). The change is its own commit, `b719728`, and touches three lines, all a consequence of the approved behaviour:
- `expect(broken.status).toBe('ephemeral')` → `.toBe('chooser')`;
- the visit-only `broken.binding!.setItem(...)` → `expect(broken.binding).toBeNull()`, because a chooser has no binding; the byte check on the truncated record is kept;

## Second-agent review

A second agent reviewed `007b039..2f1a925` for storage. It **confirmed 5 of 5** review points: correctness and the lock contract, the UI paths, that the assertion change is minimal, the sabotages, and the docs. It found nothing blocking. It also checked these paths:
- `session.setItem` throwing: chooser, with no lock held;
- a record whose `getItem` throws: visit-only, as before;
- the selected row tombstoned while the lock is awaited: chooser (it used to be a visit-only copy of a learner being deleted);
- delete, raw copy and audio export from the chooser;
- a chooser with a null binding in `main.ts` and `session.ts`, which already existed.

Seven sabotages were run. Five were caught (no lock release, a late release, the selection not cleared, only `invalid` handled, no notice). Two were not: `storage` treated as the chooser, and every error treated as the chooser.

Follow-up, in one commit:
1. **N1 (non-blocking).** If the catalogue turned `newer` or unreadable while the owner lock was awaited, the result was an empty chooser instead of visit-only. It was safe, because every write path re-reads the catalogue and throws, but the statement above was untrue for that case. The chooser branch now calls `this.catalog()` first, so a catalogue error goes to the existing visit-only catch, while a tombstoned or removed row still gets the chooser.
2. **N2 (non-blocking).** Nothing pinned that other errors stay visit-only. A new test checks two cases:
   - the selected record's `getItem` throws: visit-only, notice `storage`, no lock held;
   - the race from N1: visit-only, notice `newer`.

   Both previously uncaught sabotages ("every error goes to the chooser" and N1's fix removed) now fail it.
3. **Nit.** The user guide says visit-only happens when "the list of learners or the saved data cannot be opened at start".
4. **Nit, not changed.** The M-PLATFORM-001 test no longer re-pins that a visit-only write leaves the disk unchanged. Other tests pin it: the no-locks test in `workspace-profiles` and PR6's visit-only tests.
