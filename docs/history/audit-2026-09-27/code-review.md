# Current-source audit: Launch and analysis tools

Snapshot: `source/`, GitHub main `c03f163d4d9d93a7ac361b85b9e285730041d465`. Read-only review; no repository edits, dependency installation, full flight suite, or browser work by this reviewer. Line references below are relative to `source/`.

## Findings, in priority order

1. **P1/P2 — Returning through Home/Watch loses the saved mission from the active workspace.** High-confidence static control-flow finding; root is checking live reproduction. Set up a distinctive Engineer mission, navigate Home, reload, then enter Explore/Engineer. `src/main.ts:722-727` restores storage only when the initial launch mode is a workspace; Home, Watch, Orbit, and Build take the `lean` branch and load the featured Soyuz. `setRoute` (`:590-628`) only changes presentation, so later entering the workspace does not restore the stored mission. The next valid edit/preview overwrites the saved copy (`:1176-1179`). Preserve the user's workspace mission separately from the landing/viewer preview, or defer restoring it until entering the workspace. Direct Engineer reload should work, which is why a round-trip serialization test will miss this.

2. **P2 — Clicking a Monte Carlo point can open a different mission from the one that produced it.** High-confidence static finding. Run a set, change payload/target/vehicle/guidance in the normal setup, then click a plotted run. The non-modal window retains `job.cfg`, but `src/ui/monte-carlo.ts:638` discards the reconstructed mission except for `.dynamics`; `src/main.ts:429-431` pastes those dynamics into `panel.missionState()` from the current setup. It therefore cannot reliably reproduce the plotted result and may apply a vehicle-specific dispersion to another vehicle. Pass and restore the full reconstructed mission, or explicitly invalidate the action when the setup differs.

3. **P2 — Orbit-lifetime results stay presented under settings that no longer produced them.** High-confidence static finding, potentially shared with the Orbit reviewer. Complete a lifetime run and change mass, area, drag, horizon, method, or activity; alternatively change them while the worker runs. Handlers at `src/ui/lifetime.ts:104-151` only mutate form state and neither clear/mark the old result nor lock active-run settings. Run options are captured at `:178-183`, while the completion unconditionally assigns the result and rebuilds the form using current settings (`:189-195`). A user can read a valid chart under the wrong assumptions. Keep the analyzed inputs with the result and show “settings changed; run again”, or clear the result on edit. Numeric invalidity is also silently ignored at `:133`, while Run only checks that an orbit exists (`:160`), so negative/blank visible values can run using the previous value.

4. **P2 — The attitude-control Auto Tune still blocks the browser's main thread.** Source confirmed; a small local execution of the actual numerical routine corroborated synchronous blocking. This is the inspector's gain tuner, not the improved launch-guidance tuner. `src/ui/loop-tuning.ts:185-193` runs `autoTune` directly inside `setTimeout`; deferring its start does not yield while the search executes. It verifies every recorded model (`Infinity`, `:187`) and offers no cancellation. Actual `autoTune` with just 16 elementary two-state plants took **224.7 ms** on this machine, and a queued zero-delay timer had not run when it returned. This is a limited Node microcheck, not a browser/long-flight benchmark; flexible full-flight cases may cost more. Move it behind a worker with cancellation, run identity, and progress, following `src/physics/tune-job.ts`.

5. **P2 — Partly started Monte Carlo pools leak if a later worker creation fails.** Verified by a tiny injected-worker test of the actual `MonteCarloJob` class; its physics/data collaborators were stubbed to avoid running simulations. `src/physics/monte-carlo-job.ts:64` spawns workers in a loop without cleanup on a throw from `:70` (or `postMessage` at `:92`). The UI only acquires the job after construction succeeds (`src/ui/monte-carlo.ts:268-270`). A factory that succeeds once and throws on the second call produced `{factoriesCalled:2, posted:1, terminated:0, callbackStillAttached:true}`. The first worker keeps running, but the failed job is unreachable from Stop. Catch startup/dispatch failures, terminate the already-started pool, and report failure once. Also test replacement-worker creation failure (`monte-carlo-job.ts:81`).

## Watch click failure reported by root

Root reported live mouse/AX clicks on 100×, Choose a launch, and Another launch having no effect while the simulation advances. **No source cause established.** Current source attaches handlers (`src/ui/watch.ts:146`, `:150`, `:358`) and does not repaint those buttons per frame. `.watch-controls` and `.watch-card` explicitly restore `pointer-events:auto` (`src/ui/modes.css:277`, `:317`). The current camera handler explicitly refuses to capture pointers whose target is a button/control (`src/render/cameras.ts:132-150`), with a comment describing the old exact symptom. Verify live asset/service-worker identity and keyboard activation/hit target before attributing this failure to the current camera code. The source fix means old September findings must not simply be repeated.

## Strengths confirmed in current source

- Watch, Explore, and Engineer share a mission and simulation; switching depth does not itself replace settings. Explore exposes computed settings and identifies Engineer adjustments (`src/ui/explore.ts`, `src/ui/panel.ts`).
- The main launch-guidance auto-tuner now has a dedicated worker, AbortController, termination, stale-result protection, and cancellation on setup edits/launch (`src/physics/tune-job.ts`; `src/ui/panel.ts:2524-2535`, `:2580-2613`). Treat the old blanket “Auto Tune freezes everything” finding as obsolete for this tuner.
- Mission links/files use a versioned format, deep copies, input validation, partial-recovery notices, and watch-mission round trips (`src/config/mission-file.ts`, `tests/mission-file.test.ts`).
- Replay stores frames rather than rerunning physics, protects event boundaries, has bounded ordinary-frame history, and uses frame-backed telemetry for rewind. Whole-flight CSV/report data is separately sourced (`src/replay/recorder.ts`, `src/replay/player.ts`, `src/replay/simview.ts`, `src/ui/telemetry.ts`).
- Worker and inline launch paths share a session interface and mirrored-state tests. Physics fidelity and failure/abort/rendezvous coverage is unusually extensive for a learning application.
- CSV, PNG charts, versioned reference flights, and a self-contained printable HTML report form a useful analysis/export workflow. No current-source evidence justified declaring basic exports broken.

## Coverage and limits

The default Vitest environment is Node (`vite.config.ts:68`); heavy and 6-DOF fleet suites are separate (`:64-67`). Files named `*-ui-core.test.ts` and `*-mode.test.ts` largely test pure models, contracts, or source text, not browser interaction. Existing mission-file tests verify serialization/storage, but not Home → reload → workspace restoration. Monte Carlo tests cover normal pooling/stopping/worker death, but not partial constructor failure or restoring an old plotted run after setup edits. Add short browser journeys for persistence, Watch buttons, replay/export meaning, analysis result invalidation, and keyboard/narrow-screen use. No full suite/build was executed in this read-only review; inspected tests are evidence of coverage intent, not newly verified passing status.
