# Learning/content review — 2026-09-27

Read-only source review of the audit snapshot supplied by the parent, main `c03f163d4d9d93a7ac361b85b9e285730041d465`. No browser, installations, simulation flights, or test execution were performed by this reviewer. File/line references below are relative to `audit-2026-09-27/source`. “Confirmed” means the implementation or copy was inspected, not that a browser interaction was reproduced. Priorities are product recommendations, not security severities.

## Eight strongest findings

1. **P1 — Exported learning evidence does not preserve the mission as flown. Confirmed.** `LessonRecord.mission` promises the mission as flown (`src/lessons/progress.ts:26–27`). The UI builds that record with `guidanceOverrides: {}` and omits `cfg.rendezvous` (`src/ui/lessons/lesson-mode.ts:276–285`). The serializer simply copies these fields, including rendezvous only when present (`src/config/mission-file.ts:82–99`). Consequently the results artifact loses the student's acceleration/guidance changes and chosen docking profile. This particularly matters for aerodynamic-load lesson 2.1, which asks the learner to change guidance (`src/lessons/builtin/track2.ts:20–45`), and docking lesson 5.2, which starts with `twoDay` and asks for a faster profile (`src/lessons/builtin/track5.ts:54–68`). Preserve the resolved flight configuration or a complete reproducible override set, plus rendezvous and pad fields. Add one targeted round-trip check using a nondefault acceleration limit and a nondefault docking profile. I did not fly a reproduced export.

2. **P2 — Physics & sources has a demonstrably stale model limitation in all three languages. Confirmed.** The rendered limits paragraph says six-DOF omits slosh and structural flexibility (`src/i18n/en.ts:581`, `ru.ts:564`, `th.ts:566`; rendered by `src/ui/dialogs.ts:208`). Flexible physics already exists (`src/physics/rigid/flex.ts:2–11`, `:38–39`) and lesson 4.4 actually enables `flex: { bending: true }` (`src/lessons/builtin/track4.ts:109–124`). Replace the blanket omission with a distinction between the basic rigid model, optional slosh/first bending modes, and remaining approximations. Show the active mission's model switches. This is a trust/education issue even though the current copy understates capability rather than exaggerating it.

3. **P2 — Changing language during a placement question discards its unsubmitted answer. Confirmed control flow; needs browser reproduction.** `applyLanguage()` invokes the current redraw (`src/ui/lessons/assessment-view.ts:122–124`); `renderQuestion()` resets both `picked` and `confidence` (`:223–232`), recreates blank numerical inputs (`:319–331`), and replaces the DOM (`:137–142`). Responses persist only after Next (`:368–374`). This is particularly awkward for a Thai/English/Russian learning product where learners may switch language to understand vocabulary. Keep draft answer, multi-selection/order, confidence and focus keyed by question ID, and repaint translated labels around that draft.

4. **P2 — Some lessons grade a weaker task than their brief describes. Confirmed missing conditions; alternate passing flights not executed.** Lesson 2.4 asks for 20 Monte Carlo runs with seed 1 and replay of the run farthest from the target perigee (`src/lessons/builtin/track2.ts:120`, `:131–144`), but its hook checks only that the flight has a dispersion object with seed 1 (`src/lessons/hooks.ts:62–65`). It does not establish that 20 runs were completed or the selected run was the most extreme. Lesson 4.3 specifies a 2° pitch step held 8 s around T+65 s (`track4.ts:80`, `:101`); grading retrieves any last completed pitch step before MECO, with no amplitude/hold-time/start-time check (`src/lessons/measures.ts:72–79`, `:168–172`). Either make these conditions part of the rubric, or explicitly label them recommended experiment procedures. For Monte Carlo, ask learners to select/explain the extreme run and read the ellipse, instead of awarding “3σ” completion merely for replaying any dispersed flight.

5. **P2 — Failure feedback is least explanatory at the moment a learner needs it. Confirmed UI behavior; learning impact is an inference.** The strip shows detailed debrief only after a pass, while a fail receives one generic sentence (`src/ui/lessons/lesson-mode.ts:419–422`; `src/i18n/en.ts:2421`). Numerical mistakes reveal the expected value immediately (`lesson-mode.ts:408–410`), and another submission can produce a permanent pass (`:290–299`; `src/lessons/progress.ts:82–86`). This is acceptable formative practice, but completion alone cannot demonstrate independent understanding. Add an outcome-specific explanation with the relevant replay instant/graph: e.g. “q peaked at X, above 25 kPa; inspect speed and density at max-Q”, then a prompt to predict what changing acceleration will do. Preserve first response, corrections and hint usage separately; offer an optional new-parameter retry to demonstrate transfer. Avoid punishing useful hint use.

6. **P2 — Placement recommendations are useful, but confidence changes scores without an explanation. Confirmed.** Difficulty weights are 1/1.5/2 and a correct self-described guess earns half credit (`src/lessons/assessment/score.ts:12–14`, `:100–104`, `:134–143`). The UI offers confidence buttons without explaining that consequence (`src/ui/lessons/assessment-view.ts:343–356`; introductory copy `src/i18n/en.ts:2470`). Not choosing confidence defaults to “unsure” (`assessment-view.ts:371`), earning full credit for the same correct answer. Thus a candid “guess” scores less than leaving confidence blank. Only 4 questions per nonbasic domain determine a displayed percentage/level (`src/lessons/assessment/draw.ts:13–19`); the bars show percentage and level, not the denominator (`assessment-view.ts:413–422`). Explain scoring upfront and show “3/4 correct; confidence uncertain”; preferably separate correctness from confidence and use the latter to prioritize review. Keep the existing good policy that all lessons remain open. Domain-level mastery and before/after gains are a recommendation heuristic; I did not find calibration evidence or assess psychometric validity.

7. **P2 — Browser-only continuity is fragile and results export is not restore. Confirmed.** Progress survives reload only through local storage; reads return empty on error and writes swallow failures (`src/lessons/progress.ts:55–74`). The UI gets no saved/unsaved outcome (`src/ui/lessons/lesson-mode.ts:134–136`). Export includes results but omits custom lesson/question definitions (`progress.ts:109–115`); the only importer parses lesson files, not results (`lesson-mode.ts:692–723`). Add a small saved/session-only status, a versioned backup/restore for progress and custom content, and a meaningful resume action. Do not describe current results export as a restorable backup. Avoid an account/backend until a real multi-device/classroom requirement exists.

8. **P3 — Discovery copy and Thai terminology need a small consistency pass. Confirmed.** Home gives both Orbit and Build the same “In development” badge (`src/ui/home.ts:112–122`). Runtime routes Orbit to its actual playground and Build to the roadmap screen (`src/main.ts:600–605`); the built-items list already names O01–O04, R01–R05 and M01–M03 (`src/ui/section-plan.ts`, `BUILT_ITEMS`). A novice cannot infer this difference from the badge. Say “Available now” with concrete Orbit entry actions and mark planned subfeatures individually; keep Build explicitly future. Thai distinguishes Guidance/Navigation in the domain title (`src/i18n/th.ts:2459`, `src/lessons/catalog.ts:33`) but setup labels call guidance “การนำทาง” (`th.ts:2324–2326`) and INS navigation “การนำร่อง” (`th.ts:2141`), while lesson guidance prose uses “การนำวิถี” (`track2.ts:61–62`). These are understandable synonyms, but an engineering learner benefits from a shared bilingual glossary and exactly matching task/control names. This is not evidence that the translations are broadly incorrect.

## Strengths worth preserving

- The content is substantial: direct source counting finds **21** lesson definitions and **157** question-builder calls. `COMING` is empty (`src/lessons/builtin/coming.ts:7`). The catalogue covers orbit mechanics, guidance/navigation, failures, attitude control and advanced missions. Count and script coverage are asserted in `tests/lessons.test.ts:51–75` and `tests/assessment.test.ts:54–104`. These tests were inspected, not run in this review. Script coverage is not proof of semantic translation quality.
- Real experiments already supply engagement: bad launch timing, engine failure, payload trade-offs, navigation drift, FDIR, step response, bending, landing reserve and docking profiles. The best next feature is an experiment notebook comparing baseline/change/result and linking each result to the replay, not unrelated badges or points.
- The grader is tied to the simulated flight, checks locked configuration and freezes final answers so replay scrubbing does not change results (`src/lessons/grader.ts:1–10`, `:138` onward; `src/ui/lessons/lesson-mode.ts:243–268`). There are both solved and wrong-flight tests across tracks (`tests/lessons.test.ts:85` onward, `tests/lessons-round2.test.ts`, `tests/heavy/lessons-sixdof.test.ts`). Their existence is evidence of intent and coverage, not a fresh green test result.
- The placement test has varied formats, seeded draws, prerequisite-aware recommendations, “don't know”/skip choices, and explanations plus related lessons in review (`src/lessons/assessment/draw.ts:94–119`, `score.ts:157–178`, `src/ui/lessons/assessment-view.ts:479–504`). An unfinished submitted-answer sequence resumes (`assessment-view.ts:129–134`).
- Model/data honesty is present in many good places: charts explicitly say they come from this simulator (`src/i18n/en.ts:2509`), Apollo's lesson explicitly says the Moon's gravity is not modelled (`src/lessons/builtin/track5.ts:160–165`), Newton's cannon discloses no air/no Earth rotation (`src/i18n/en.ts:933`), and Physics & sources says guidance is educational and estimates do not imply uniform accuracy (`:581`, `:585`). Repair the stale paragraph rather than removing these valuable explanations.
